1Architecture

A single Next.js application, server-rendered, with one managed PostgreSQL database and one storage account. There is no separate API tier, no queue, no cache server and no container orchestration: at a few thousand profiles and a consultant team of three, each of those would be cost and surface area with nothing to pay for it.

ComponentWhat it is, and why
ApplicationNext.js 16 on Node 22, TypeScript, Tailwind. Server components render every page; server actions handle every write, with Zod validation on the server, so no business rule depends on the browser. Deployed as the standalone bundle (≈ 17 MB zipped) and started with node server.js.
HostingApp Service plan Basic B1 (1 core, 1.75 GB), Linux. Always On, HTTPS only, TLS 1.2 floor, FTPS off, container logging on. The smallest tier that keeps a process warm; the next step up is one command (§4.4).
DatabasePostgreSQL 17, Burstable B1ms, 32 GB storage, 7-day automated backups. The free-tier SKU for twelve months on a new account. All access is through the application's own connection pool over enforced TLS; the browser never talks to the database.
Data accessOne module, src/lib/db/: a pg pool with type parsers (client.ts) and a table-agnostic CRUD layer (crud.ts) that every data module in src/lib/data/ is written against. Values are always bound parameters; identifiers are pattern-checked; updateMany and deleteMany refuse to run without a filter. Three hand-written statements remain, each commented as to why.
StorageStandard LRS, hot tier. Three private containers. Nothing is reachable without a SAS token the server mints per render, valid one hour, computed locally (an HMAC — no round trip). Deleted blobs are kept 14 days.
PhotosEach photo is three blobs: the original (kept, never shown), a 480 px WebP thumb for grids and cover tiles, and a 1200 px WebP medium for the carousel, slideshow and share page. Both copies are made once, at upload, by sharp; pages serve them directly. The server never resizes on request.
UploadsStraight from the browser to Blob Storage. The server issues a write-only SAS for a path it chose; the browser PUTs; the server then reads the blob back inside the datacenter, confirms it is an image, writes the two copies and records the row. A failure at any step deletes what was written. The App Service never buffers an upload.
Identity & sessionsOne administrator password (bcrypt hash in configuration); a signed, HTTP-only session cookie, 12 hours. Families are identified by name and phone, held in a signed cookie, matched to the client book by normalised phone number.
DeploymentGitHub Actions on every push to main, signing in to Azure with OpenID Connect through a user-assigned managed identity that holds Contributor on the web app alone. No credential is stored anywhere.
Development backupVercel, branch vercel-dev — the last Supabase-based commit. Not production; vercel.json on main stops Vercel building it.

1.1 Security model

  • Network. The database firewall admits Azure-internal sources (the 0.0.0.0 sentinel) and the operator's IP; the public internet is refused before any password is checked. Public access can be replaced with a private endpoint (≈ ₹700/month) if a contract ever demands no public endpoint.
  • Data. Row-level security is enabled on every table with no policies; the application connects as the table owner, which bypasses it; any other role is denied everything.
  • Media. Private containers; one-hour SAS for reads; ten-minute create/write-only SAS scoped to a single server-chosen path for uploads; CORS limited to the site's origin.
  • Disclosure. Share links carry one of three access levels enforced field by field on the server. Finances, internal tags, Aura and Urgent markers, potential-client markers, the middleman's details and private notes are never serialised to a client page at any level.
  • Secrets. Live only in App Service configuration (encrypted at rest, RBAC-protected) and in the operator's git-ignored azure/.env.azure. Not in the repository, not in GitHub, not in CI logs.

2Configuration

The application reads everything from environment variables, so nothing about where it runs is in the code. In production those are App Service application settings; locally they are .env.local. azure/infra.sh writes the infrastructure-derived ones, and azure/deploy-local.sh pushes the application secrets from the operator's .env.local.

3Deployment

3.1 From a push to main (normal)

  1. Merge or push to main. Pull requests only build and type-check; they never deploy.
  2. GitHub Actions, on a Linux runner: npm ci, generate route types, type-check, lint, next build as a standalone bundle with NEXT_PUBLIC_SITE_URL baked in, zip (under UTC), publish the artifact.
  3. The deploy job signs in with OIDC, zip-deploys to the web app, then polls /browse for up to ten minutes and fails the run if the site does not answer — App Service itself reports success as soon as the zip lands, before the container has restarted.
  4. Watch it: gh run watch, or Actions on GitHub. A deploy takes four to eight minutes end to end.

3.2 From a laptop (when GitHub is unavailable, or for a quick fix)

./azure/deploy-local.sh                # build, push .env.local secrets, deploy, poll
./azure/deploy-local.sh --no-build     # redeploy the last build
./azure/deploy-local.sh --skip-settings

Identical result, except that a Mac-built bundle runs sharp on its WebAssembly fallback (slower resizing on upload; the CI build uses the native Linux binary). Prefer the pipeline.

3.3 Database changes

Schema changes are SQL files in supabase/migrations/, numbered and re-runnable, and are applied by hand with psql "$DATABASE_URL" -f supabase/migrations/NNN_….sql before the code that needs them is deployed. supabase/setup.sql is the whole schema in one file for a new environment, and must be kept in step. Take a backup first (§5.2).

3.4 Scaling

az appservice plan update -g anurupa-rg -n anurupa-plan --sku B2            # 2 cores, 3.5 GB
az postgres flexible-server update -g anurupa-rg -n anurupa-pg-8c72e8 \
    --sku-name Standard_B2s --tier Burstable                                 # in place; a restart, no migration
az postgres flexible-server update -g anurupa-rg -n anurupa-pg-8c72e8 --storage-size 64   # grows; never shrinks

At the volumes in the cost sheet none of this is needed; the figures hold to roughly 25,000 profiles. Storage of photographs is not a scaling concern at all — ten thousand HD photos is about 50 GB and about ₹100 a month.

4Rollback

Rollback means putting the previous working version back after a deploy turns out to be wrong. On this platform the application and the data roll back separately, and the application side is quick because every deploy is a complete, self-contained bundle.

4.1 Application — three ways, fastest first

SituationDo this
Last deploy is bad; the one before was fine, within 7 daysRe-run the previous green run's deploy job. Its artifact is still there, so nothing is rebuilt:
gh run list --branch main --limit 5 → note the id of the last good run →
gh run rerun <id> (or in GitHub: the run → Re-run all jobs). Five minutes.
The bad change should be undone in history toogit revert <bad-commit> and push. The pipeline deploys the reverted code. This is the one to prefer when others will keep working on main.
GitHub is unavailablegit checkout <last-good-commit> then ./azure/deploy-local.sh. Afterwards return to main.

In every case, confirm with the smoke test the pipeline does: curl -sI https://anurupa-8c72e8.azurewebsites.net/browse should return 200, and the admin should be able to sign in.

4.2 Configuration

A bad application setting is corrected with az webapp config appsettings set (§2); the app restarts on its own. There is no history of settings in Azure, so the values to restore are in azure/.env.azure and .env.local — keep those files.

4.3 Database

Migrations are forward-only: there are no down-scripts, because a column that has held data cannot be un-added without losing it. If a migration must be undone, write a new migration that reverses it. For the data — a bad bulk import, a cleanup that went too far — use point-in-time restore (§5.3), which returns the database to any minute of the last seven days.

Order matters. If a release included a migration, roll the application back first; the old code tolerates extra columns, but new code cannot run against the old schema.

5Backup & restore

5.1 What is protecting the data, today

Nothing here is off-site in the geographic sense: all of it is in Azure Central India. For a matchmaking consultancy that is the right trade; if a copy outside Azure is ever wanted, a weekly ./azure/backup-db.sh --keep-local and a copy of azure/backups/ to any drive is it.

5.2 Take a backup

./azure/backup-db.sh                 # pg_dump → db-backups/anurupa-<UTC time>.dump, lists what is stored
./azure/backup-db.sh --keep-local    # and keep the file in azure/backups/

Custom format, compressed, about 330 KB at today's size. Recommended cadence: before every migration or import, and weekly otherwise. There is no scheduler for it yet; a calendar reminder is honest about that.

5.3 Restore the database to a point in time (preferred for "undo")

# 1. a NEW server, restored to the moment you choose (UTC); 10–20 minutes
az postgres flexible-server restore -g anurupa-rg --name anurupa-pg-restored \
    --source-server anurupa-pg-8c72e8 --restore-time "2026-10-13T05:50:00Z"
# 2. same firewall rules as the original (infra.sh's "Database firewall" step, or the portal)
# 3. point the app at it, then restart
az webapp config appsettings set -g anurupa-rg -n anurupa-8c72e8 \
    --settings DATABASE_URL="postgresql://anurupa_admin:<password>@anurupa-pg-restored.postgres.database.azure.com:5432/anurupa?sslmode=require"
# 4. update azure/.env.azure to match; delete the old server once satisfied

The restored server keeps the original's admin password. Nothing on the original is changed by this, so it can be compared first.

5.4 Restore the database from a dump

./azure/restore-db.sh                                   # list backups
./azure/restore-db.sh anurupa-2026-10-13T06-38-41Z.dump  # into production — asks you to type the host name
./azure/restore-db.sh <name> --into "postgresql://…"    # into any other database, e.g. a rehearsal
az webapp restart -g anurupa-rg -n anurupa-8c72e8        # afterwards, so the pool reconnects

The restore is one transaction: either the whole backup lands or nothing changes. This procedure was rehearsed before being documented: the first backup was restored into a scratch database on the same server and matched production row for row (2,783 profiles, 11 clients, 23 photos, 9 links).

5.5 Recover a deleted photo, or rebuild everything

# a photo deleted in the last 14 days (all three of its blobs)
az storage blob undelete --account-name anurupast8c72e8 -c profile-photos -n "<profile-id>/<uuid>.jpg"
az storage blob undelete --account-name anurupast8c72e8 -c profile-photos -n "<profile-id>/<uuid>.thumb.webp"
az storage blob undelete --account-name anurupast8c72e8 -c profile-photos -n "<profile-id>/<uuid>.medium.webp"
# the row in profile_photos is restored with the database (5.3 or 5.4)

# a whole new environment, from nothing
./azure/infra.sh                        # resources + schema
./azure/restore-db.sh <dump>            # data
azcopy copy "https://<old>.blob.core.windows.net/profile-photos?<sas>" \
            "https://<new>.blob.core.windows.net/profile-photos?<sas>" --recursive   # media
./azure/deploy-local.sh                 # application
